# Document lifecycle

What each kind of doc holds and how it's written. When a doc needs syncing is in the root CLAUDE.md, [Keeping docs in sync](../CLAUDE.md#keeping-docs-in-sync).

## Breadcrumb

Docs under `docs/` and the folder READMEs open with a breadcrumb line above the title (`[README](../README.md) › parent › page`). Area docs sit under the architecture doc (`#building-blocks`), specs under the roadmap, everything else directly under the README. The root README and the CLAUDE.md files have none. Don't write breadcrumbs by hand: after creating, renaming or retitling a doc, run `./scripts/docs_check.py --fix`. The pre-commit hook runs it with `--check`, which also fails on a broken relative link or `#anchor` in the docs.

## Architecture doc

`docs/architecture.md` (arc42-lite) holds the decisions that are expensive to reverse or span several areas (stack, data model shape, styling approach), each with its reason and, where still useful, the rejected alternatives; plus goals, constraints and risks. Current state only: a changed decision is rewritten in place, and what it replaced moves into its "Rejected" line if the reason still matters; git keeps the old text. A decision is written in when it's made, with the spec that acts on it citing its section; until it's built, the section says it's planned. No spec numbers or completion status. A decision that concerns one area only goes in that area doc's Decisions instead.

## Spec

A spec (`docs/specs/NNNN-*.md`) is one bounded unit of work (a scaffold step, a feature slice), used to plan and build it. Temporary: it lives until its roadmap phase closes, then gets folded into area docs and deleted. Numbers aren't reused: the next one is above the highest in `docs/specs/` and in git (`git log --all --name-only -- docs/specs`), since folded specs are gone from the folder. After the breadcrumb and title, a `## Status` section opens it, with the state on its first line (`Draft`, `Approved`, `Done — YYYY-MM-DD` or `Abandoned`), then:

- `Phase:` the roadmap phase it belongs to (or `Scaffold/Infra` for non-feature work; these have no phase to close, so they fold into [development.md](development.md) once done)
- `Card:` the id of its backlog card. The card names the spec back in a `Spec:` line, as the path in backticks, not a link, since the card moves to `backlog/done/`. Small items have only the card.
- `Architecture:` the section(s) of the architecture doc it draws from, as links, if relevant
- `Superseded-by: NNNN (scope)` — when a later spec reverses part of this one before it has been folded. `(scope)` says exactly what's reversed. Once the later spec is folded, the pointer names its phase and area doc instead (`Superseded-by: Phase 2, see [<area>](../areas/<area>.md) (scope)`). The fold resolves it; no reverse pointer is needed. A change made without a spec of its own points at the doc that now describes it: `Superseded-by: see [<area>](../areas/<area>.md) (scope)`.

The sections after Status are `## Goal`, `## Done means`, `## Tests`, `## Explicitly out of scope` and `## Decisions` (a list led by bold titles, not numbered; other text cites a decision by its title), then an optional `## Implementation order` for a build split into commits. Slices, if any, are described in the Goal.

## Area doc

An area doc (`docs/areas/<area>.md`) is a conceptual sketch of how one part of the app works today: its concepts, flows, states and edge rules, plus the few decisions worth pointing out. Repo setup, tooling and the reasons behind them are in [development.md](development.md) instead, not in an area doc, so they're written down once. No completion status, history or "later change" notes; git keeps those. There is no fixed template; the existing area docs show the style. Beyond that:

- Leave out what the code, UI or API schema already hold (exact UI strings, parameter lists, lists of tested modules), and keep what it can't say: the why and the edge rules.
- "Where to start reading" lists the entry points only, a handful, each with one line on what it's for. The docs check catches a dead link, not a description that no longer fits.
- A decision goes in only if one of these holds: it rejects an alternative someone would plausibly suggest again; it spans several modules, so no single code comment has a natural home; or reversing it would break stored data or something non-obvious. Otherwise the reason is a short comment at the code it explains, or left out when the code already makes it obvious. A look-and-feel choice is provisional unless it carries a reason. If a decision seems worth recording but fails this, raise it with the user instead of adding it.
- Decisions are led by a bold title, not numbered; code comments and other docs cite one by its title, so lists can be pruned and reordered freely.
- One fact in one place within a doc too: a section doesn't restate the reason of a decision, and a behaviour bullet doesn't paraphrase the decision it cites.
- No Tests section. A test gap that is a real risk is a line under architecture › Risks.
- "Not built" lists only what's deliberately left out and isn't a roadmap or backlog item yet; those items get a link (the `backlog/` folder, not a card file).
- A Mermaid diagram only where it replaces text, checked against the code and rendered to check the syntax (a scratchpad HTML page loading `mermaid@11.4.1` from cdn.jsdelivr.net, screenshotted with a headless browser).

## Folder README

A folder README (`<folder>/README.md`, for each folder with its own toolchain, and `scripts/`) holds setup, layout, conventions and tooling reasons for that folder. [development.md](development.md) links to it from its Layout section instead of repeating it, and keeps only what spans folders. How the app behaves stays in area docs. When a section of development.md grows to concern only one folder, propose moving it there. The root README is upstream's Marketplace page and is not part of this.

## Fold at phase close

Once a phase closes (see [Backlog](#backlog)), move it into the roadmap's Shipped list and, for each of its specs: move what is still current and worth keeping into the area doc(s) it belongs to, check that text against the code rather than the spec, then delete the spec. A spec is more detailed than an area doc should be: sketch the behaviour, run each decision through the area doc's filter above, and don't carry something over just because the spec wrote it down. A new area doc also gets a link from the architecture doc's Building blocks section, which its breadcrumb points at. A spec that also covers an area whose phase is still open can wait for that phase. The other way round, a spec whose content is all in area docs already (e.g. folded with another phase's specs) can be deleted before its own phase closes. Point references (roadmap, other specs, code comments) at the area doc. Old spec text stays in git (`git log --all -p -- 'docs/specs/NNNN-*'`). After the fold, ask the user to run `/docs-consistency`.

## Roadmap

`docs/roadmap.md` holds the why and the order; the backlog holds the what. Update it when scope or phase priority actually changes, not on every commit. It holds the vision and workflow, a Shipped list with one line per closed phase (date, area docs, not spec numbers), and the open phases, each with a goal, why it comes now and a "Done when" list of items that can be ticked off at the close. No status lines: the cards hold the status.

## Backlog

`backlog/` holds one markdown file per item (feature, fix, idea), all in one flat folder, shown as a board by the Kanban Markdown extension. The file name is the card's `id`, which other text uses to name a card in backticks. Docs link the `backlog/` folder, never a card file; only cards link each other (see Dependencies). The docs check lints the frontmatter below. Frontmatter fields:

- `epic`: the roadmap phase as `"<NN> <name>"`, two digits so the epics sort right (`"01 First Release"`); `null` means later. "Phase" is the roadmap's word and "epic" the board's for the same unit. `"XX <name>"` groups cards that aren't a planned phase yet: it sorts after the numbered epics and before `null`, and gets a number once it becomes a roadmap phase. Per area there are two kinds. `"XX <Area> vN"` is a planned version of that area, numbered on: `"XX Board v2"` is the next one, and a `"XX Board v3"` can open early for what is sure to come after it. When a version becomes a roadmap phase, its number isn't reused, so the next one up is v3. `"XX <Area> Future"` (`"XX Board Future"`) is what might come some day. `null` is for a card that fits no group. A phase renumbering means rewriting `epic` on its cards. A numbered epic holds only what has to be done before its phase closes, since a phase closes when its epic has no open card; "do this soon" is `priority`, not a place in an epic.
- `status`: one of the columns set in `kanban-markdown.columns` in `.vscode/settings.json`: `backlog` unless started, `ready` once the card meets the Definition of Ready (only `/refine` sets it), `in-progress`, `done`. A card whose `status` names no column doesn't show on the board.
- `priority`: `critical`, `high`, `medium` or `low`, set during refinement. `order` is the order within the epic. Until `equal-order-keys` (Phase 1) ships, every `order` key is unique across the whole board, since the installed 1.14.1 throws when two neighbouring cards share one. Picking the next card: priority first, across epics; then the lowest open epic (numbered, then `XX`, `null` last); then `order`.
- `labels`: one kind (`feature`, `enhancement`, `bug`, `idea`, `chore`) and one area (`extension` for the host and `src/shared`, `webview`, `infra`, `workflow`).
- Dependencies: a `**Needs:**` line in the body listing card ids, each a link to the card's file (``[`some-card`](some-card.md)``). Not a frontmatter field: the extension rewrites the frontmatter from its own fields when a card is edited on the board, so an extra field would be lost. Grep `Needs:.*<id>` finds the cards waiting on one. Every other mention of a card in a card's body is a link too, so the board's preview can jump to it. Write the id in backticks and run `./scripts/docs_check.py --fix`: it makes the link, and repoints it when the card moves into `backlog/done/` (or out of it). The check fails on a `Needs:` id that names no card. `Needs:` names what has to exist before the card can be built, not what it merely touches or resembles.
- **Definition of Ready.** A card is ready when it has: its goal in one or two sentences from the point of view of the person using the product (the developer's, for workflow cards); a `**Done when**` list that can be ticked off; no open questions, each one answered or deferred to a named card; its `**Needs:**`; a size that fits one branch, otherwise it's split into cards or says "spec with slices"; and whether it needs a spec first or can be built directly (see [Scope Control in the root CLAUDE.md](../CLAUDE.md#scope-control--risk-guardrails)). An `**Out of scope:**` line is optional, for an obvious temptation. A ready card is still short: refinement doesn't write the spec into it.
- Started: `/branch` sets `status: "in-progress"` in its own commit, `docs(backlog): start <id>`. A branch is named after its card.
- Finished: its own commit, `docs(backlog): finish <id>`, after the work (the last slice's, for a card built in several branches). It sets `status: "done"`, `completedAt` and `modified`, and moves the card into `backlog/done/` with `git mv`, the state the extension produces on load. With the board open, the extension moves the card itself as soon as `status` is `done` (stage the move with `git add -A backlog`), but leaves `completedAt` and `modified` as they were, so set those by hand. The docs check skips that folder. The code commits stay free of `backlog/`, so they cherry-pick onto upstream (see [Fork and upstream](../CLAUDE.md#fork-and-upstream)).
- Parking an idea means a new card, two or three lines, `status: "backlog"`, with the `epic` and `labels` that fit the idea (asked, not assumed `null` and `idea`). Not a memory or a roadmap line. `/park` writes one.
- A phase closes when its epic has no open card (none outside `done`) and each "Done when" item in the roadmap holds; an item that doesn't becomes a card in that epic, so the phase stays open. Then, together with the fold, its done cards are deleted, so its epic leaves the board; git keeps them. Unfinished cards of a closed phase stay, moved to another `epic` or `null`.
- Agents find cards with Grep on `epic:` or `status:`.
- **Grooming the board.** The docs check covers the mechanical part (frontmatter, `Needs:` ids, card links, `order` unique per epic; board-wide uniqueness is by convention, see `priority` above); `/docs-consistency` compares cards with the roadmap. The rest is a session with the user, after a run of parked ideas or before a `/refine` round. Look for: duplicates and overlaps; cards that are a decision or a note, not work; cards that are only a title (still wanted?); "revisit if …" cards whose trigger has happened; cards that wait on other work happening anyway (a card stands on its own: its priority and refinement decide when it's done); a label vocabulary that no longer fits; an `XX` epic ready to become a roadmap phase, and whether the roadmap order still holds; enough `ready` cards ahead, and at most one `in-progress`. If a session keeps following these steps, turn them into a skill.
